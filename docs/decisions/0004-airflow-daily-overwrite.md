# 0004. Airflow 일별 배치는 날짜 단위 덮어쓰기로 멱등성을 보장한다

- 상태: 채택
- 날짜: 2026-09-26

## 배경
dbt → Spark 집계 → 적재 → 이상 탐지 → 품질 리포트를 매일 순서대로 돌리고, 지난 날짜도 다시 돌릴 수
있어야 한다(백필). 백필이 필요한 대표 상황은 **지연 이벤트**다. 검색 로그의 약 4%는 10~120분 늦게
도착하므로, 자정 직후 돌린 배치에는 그날 이벤트 일부가 빠져 있다.

백필이 안전하려면 같은 날짜를 몇 번 돌려도 결과가 한 벌만 남아야 한다. 0003 에서는
`ReplacingMergeTree` 가 이를 맡았지만, 중복 정리가 백그라운드 병합 때 일어나서 병합 전에는 `FINAL` 없이
세면 행이 두 배로 보인다. 그리고 늦게 온 이벤트 때문에 **세션 구성이 바뀌면** 예전 키의 행이 남는다.

## 결정
1. 날짜를 받는 모든 단계(적재, 이상 탐지, 품질 리포트)는 **그 날짜의 기존 행을 지운 뒤 다시 넣는다.**
   (`DELETE FROM ... WHERE event_date = {d:Date}` → `INSERT`)
2. Spark 는 착지 파일 전체를 읽고 `event_time` 으로 그날 것만 고른다. 늦게 도착한 이벤트가 착지 파일에
   추가되면 그 날짜를 다시 돌리는 것만으로 원래 날짜에 들어간다.
3. 세션은 **시작한 날짜**에 속한다. 자정을 넘긴 세션을 `event_date` 로 자르면 두 조각이 되어
   지표가 틀어지고, 날짜별 실행끼리 같은 세션을 나눠 갖게 된다.
4. Airflow 는 LocalExecutor 로 돌린다. 단일 머신에서 병렬 실행이 되고 Celery·Redis 가 필요 없다.
5. dbt·PySpark 는 Airflow 와 다른 venv 에 설치하고 BashOperator 로 호출한다.

## 이유
- "두 번 돌려도 같은 결과"를 병합 시점에 맡기지 않고 저장된 행 자체로 보장할 수 있다.
  품질 리포트가 `FINAL` 없이 행 수를 세서 이것을 매번 확인한다.
- 스케줄은 `CronDataIntervalTimetable` 이다. 9/26 00:00 실행이 9/25 구간을 처리하고 `ds` 가 곧
  처리 날짜라서, 스케줄 실행·백필·수동 실행이 같은 날짜 규칙을 쓴다.
  (Airflow 3 의 기본 cron 스케줄은 data interval 이 없어 `ds` 가 실행 당일이 된다)
- dbt 와 Airflow 는 의존성이 자주 부딪힌다. 환경을 나누면 한쪽을 올려도 다른 쪽이 깨지지 않는다.

## 감수하는 것
- 지우기와 넣기가 하나의 트랜잭션이 아니다. 그 사이에 실패하면 그 날짜가 잠시 비어 있다.
  재시도(2회)와 품질 리포트의 `sessions_present` 점검이 이 상태를 드러낸다.
  완전히 원자적으로 바꾸려면 임시 테이블에 쓰고 `REPLACE PARTITION` 으로 교체해야 하지만,
  `mart_search_daily` 는 날짜 파티션이 아니어서 이번에는 적용하지 않았다.
- 착지 파일 전체를 매번 읽는다. 데이터가 커지면 착지 경로를 `dt=` 로 나누고 대상 날짜와
  다음 날 파일만 읽도록 바꿔야 한다.
- 속도 신호의 z-score 가 그날 세션 집단 기준이라, 전체 기간으로 한 번에 판정한 결과와 조금 다를 수 있다.
  이는 "그날 트래픽 분포에서 튀는 정도"를 보려는 원래 설계(`abuse.py`)와 같은 방향이다.
